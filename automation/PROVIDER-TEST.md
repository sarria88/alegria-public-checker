# Isolated hosted provider test

Run Actions → External public checker → Run workflow → operation `provider-test`, on main. The cron and the default operation remain production `cycle`; this test has a separate concurrency group and never restores or writes production monitor state. No production website, API endpoint or completion heartbeat is failed or pinged by the test.

This manual operation uses the existing team Incidents API token and requester secret. It creates one clearly `[TEST]` incident through the same adapter, with fresh test-only state and unique run-ID plus attempt metadata. Manual reruns use a different attempt identity, so cleanup cannot confuse a new resource with an older paused test. Synthetic first FAIL does not alert; a second non-PASS creates a pending event. An injected channel exception must remain sanitized and pending; the actual provider retry then creates the labeled incident. The first PASS leaves it open; the second PASS resolves it. API state is checked separately from mailbox delivery.

The operation creates one disposable `[TEST]` heartbeat with period 30 seconds, grace zero and email enabled, within the free quota. It sends its first test-only heartbeat, then waits up to 100 seconds for real elapsed-silence detection. It independently exercises the supported `/fail` simulation and recovery. A URL equal to the production completion secret is rejected before use. The test heartbeat is paused afterward, never deleted; the test incident is resolved, with narrowly scoped reconciliation of lost acknowledgements. A failed or timed-out workflow may require operator cleanup of its exact TEST resources. Repeated tests consume paused heartbeat slots; no paid plan is selected.

Only a bounded encrypted receipt is uploaded for seven days. Raw IDs, provider bodies, credentials and heartbeat URLs are not logged or written into the receipt. Public logs and the job summary show only the overall TEST outcome, fixed per-check PASS/FAIL/INCOMPLETE values, a fixed failure-stage label and an optional numeric HTTP status. Unknown diagnostic names or raw errors are excluded. The receipt uses the existing AES-GCM artifact key and is uploaded only after the storage preflight succeeds.

Afterward, independently verify alert and recovery messages in the intended recipient mailbox. Provider API state alone does not prove email receipt. The accelerated 30-second test demonstrates only that test threshold: it does not prove production silence strictly greater than twelve minutes, evaluation at least once a minute, or recovery after two completed cycles. Native heartbeat recovery remains immediate after the next ping. The injected channel failure is a controlled transport simulation, not an actual outage of the external mail channel.

No application deployment, protected merge, production-state reset or credential creation is part of this change.
